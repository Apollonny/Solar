# Solar 3D gameplay

1. Inspect the main scene, camera, world environment and existing input before editing. Preserve the project's style, scale and rendering settings.
2. Build one visible mechanic with a ground/space reference, readable player/object silhouette and an enabled Camera3D. Remove `StarterScreen` when the game replaces it; instantiate the playable content under `main.tscn`.
3. Apply `solar-ecs`. Store movement/health/action data in components; compose physics and visual nodes in entities; implement gameplay in systems. Adapt upstream controller examples to this ownership model.
4. For physics movement, use the body's velocity and `move_and_slide` in the physics loop. Compute movement relative to the chosen camera/world basis, normalize diagonals where intended, and keep gravity/jump semantics consistent with the installed engine.
5. Give physical objects correct collision shapes, layers and masks. Keep triggers separate from solid geometry. Match the user's first-person, third-person or top-down perspective.
6. Check camera placement, clipping, lighting and visible materials before attributing a blank scene to performance. Keep a small coherent environment; do not generate large asset sets before the core interaction works.
7. Use existing models or styled primitive meshes initially. Load `solar-assets` for custom art or generated models. Keep face counts and texture sizes suitable for interactive rendering.
8. Save and call `project_validate` for the changed scripts/scenes. If runtime checks are permitted, inspect the rendered view, motion/collision, relevant state and logs. Stop the test run afterward.

Search upstream guidance for `characterbody 3d`, `camera`, `physics`, `lighting`, `materials` or the requested mechanic. Verify engine APIs; the library's Godot 4.7+ examples are reference material, not automatically compatible drop-in scripts.
